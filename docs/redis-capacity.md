# Redis capacity for secret creation

Okuru stops creating new text secrets when the number of keys in its selected Redis database reaches `OKURU_REDIS_SECRET_MAX_KEYS`. The default is 2,048 keys; configure a strictly positive integer appropriate for the deployment. Invalid values fail closed with HTTP 503. The Redis account must be allowed to execute `DBSIZE` from Lua as well as the existing hash, expiry and deletion commands.

The database key count and creation of a new secret are checked in one Redis Lua script. This coordinates concurrent Okuru processes using the same database and includes keys created before this version. Expiry and deletion naturally free space. A read or permission error prevents creation. Existing share links and their Redis records are not modified by the capacity check. Protected file uploads also create an associated text secret and are subject to this admission limit.

Web and API text-secret creation share fixed-window limits of 50 requests per public source and 400 requests globally per 24 hours. A loopback, private, carrier-grade NAT or link-local identity may represent an unconfigured proxy, so it receives the global budget rather than the smaller per-source budget; this avoids treating every user behind that proxy as one client but weakens protection until a reliable public identity is configured. Requests return HTTP 429 when a budget is exhausted and HTTP 503 when admission cannot be checked. Fixed windows can permit a burst across a window boundary; these budgets do not stop distributed sources and are not a substitute for an edge rate limit. Source identity is derived from the connection and only from explicitly trusted proxy addresses; a shared proxy or NAT can group multiple users into one budget. `OKURU_TRUSTED_PROXY_CIDRS` must accurately describe trusted reverse proxies, which must sanitize or append forwarding headers. Hashed addresses in short-lived Redis counters are pseudonymous rather than anonymous.

This is a conservative **database-wide key-count admission limit**, not a precise Redis byte quota or a per-client limit. It counts unrelated applications' keys, file metadata and download sessions too, so a dedicated Redis database is recommended. Non-secret writes and other Redis clients do not consult this limit and can cause the database to exceed it. The existing per-secret 32 KiB input limit and maximum seven-day TTL bound new secret size and lifetime, but do not establish a hard bound on Redis memory, fragmentation, other data or background overhead.

Operators should separately configure and monitor a Redis `maxmemory` budget suitable for the host, and evaluate `noeviction` to avoid silently evicting live share records. This change does not modify Redis server configuration or eviction policy. Monitor memory, evictions, rejected writes and key count; a full or unreachable database can make new shares temporarily unavailable.
