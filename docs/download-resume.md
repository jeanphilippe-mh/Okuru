# Download continuation

An authenticated download POST reserves one view as before. Once the archive has been opened and authenticated, the server creates a continuation session and sends its random key in a session-specific `Secure`, `HttpOnly`, `SameSite=Strict` cookie scoped to that file URL. A GET to the same URL with this cookie and a single `Range: bytes=…` header requests a continuation. Multiple sessions for the same link have different cookie names and validators; `If-Range` selects the right session. If multiple sessions are present and the client does not send a recognizable `If-Range`, the request is refused rather than using the wrong session. Original unencrypted ZIP links continue to use their previous `http.ServeContent` behavior for the initial POST, including multi-range requests. Encrypted archives use age random-access decryption: the header and final chunk are authenticated before the length is used, and each subsequently read chunk is authenticated. If writing or authentication fails after response headers are sent, the HTTP response is aborted.

A continuation does not consume another view. It is limited to 32 requests and to a cumulative amount of data actually handed to the HTTP writer no larger than the ZIP size. The server reserves the requested bytes atomically before writing and refunds bytes it did not write, including on an interrupted connection. A process crash or Redis failure can leave a reservation charged; bytes handed to the local writer are not proof of receipt by the client. A session can therefore permit an initial copy plus up to one ZIP's worth of repeated bytes. This is not a guarantee that only one copy exists: anyone allowed to receive a file can copy it, and a session cookie can itself be shared.

The default continuation lifetime is four hours. `OKURU_DOWNLOAD_SESSION_TIMEOUT` can set a Go duration between one second and 30 days; the session never intentionally outlives the remaining file TTL. An invalid setting fails a download before reserving a view. A long transfer that outlives its continuation session or the file TTL cannot be resumed through that session. Existing open transfers can continue after revocation; future requests require the parent record, its valid link key and an unexpired session.

Redis stores separate `download_session_<file UUID>_<SHA-256 of cookie key>` hashes. The hash contains the archive secret encrypted with the random cookie key, never the cookie key itself. The parent file record stores only a bounded index of session-key digests. The session hashes expire independently no later than the parent TTL or configured session lifetime. An authenticated deletion removes the file record, any separately shared password and its indexed sessions using one Redis `DEL`; ACL denial for any key fails the operation before any of those records is removed. File expiration also prevents future continuation; sessions have their own expiry as a backstop. Never log or expose the share link or cookie.

The Redis account must be authorized for the new key pattern and for `EVAL`/`EVALSHA`, `HGET`, `HGETALL`, `HSET`, `HINCRBY`, `EXISTS`, `TTL`, `PTTL`, `PEXPIRE` and `DEL` on the applicable file, password and download-session keys, in addition to the existing commands. Redis is needed when creating and continuing a session. A Redis failure after a view has been reserved can prevent the initial response from being sent; this fails closed rather than exposing an unlimited download. Check deployment ACLs before enabling this version.

The server supplies an ETag derived from the archive's stored representation and session and supports `If-Range`. For a legacy plaintext ZIP, computing this validator reads and hashes the **entire** stored ZIP for each initial download and continuation; this can create substantial disk I/O for large files. Size, file identity and modification time are checked after hashing and after reading, but cannot enforce immutability against an uncooperative writer with direct filesystem access. Encrypted age archives authenticate each returned chunk, but original plaintext ZIPs retain their original lack of cryptographic integrity protection. Range continuation is designed for browsers and download clients that preserve the scoped cookie and validator; actual behavior should be verified with each supported browser and proxy. No specific client, TLS termination or production deployment is established by unit tests alone.
