# Download continuation

The download form submits a POST to the share URL. Okuru checks the link and any required password, opens the archive, and reserves one view. A successful POST returns a `303 See Other` redirect to a session-specific download URL. The browser follows it with a GET and receives the ZIP as an attachment. The form works without JavaScript. To continue the same view, use the browser’s resume action on the existing download. Submitting the form again requests a new view. Opening the original share URL still displays the confirmation page.

The redirect also sets a `Secure`, `HttpOnly`, `SameSite=Strict` cookie scoped to the exact download path. The download URL contains a digest that identifies the session. The cookie holds its random key. The first GET with this cookie starts the full response. To continue an interrupted transfer, the browser requests the same URL with the same cookie and a single `Range: bytes=…` header. A valid range with a matching validator (or no validator) receives `206 Partial Content` and the session's ETag. A plain GET cannot start a second full transfer after the first response has begun. Sessions established by an older server can still use their original URL, cookie and validator until they expire.

For both supported archive formats, Okuru authenticates the age header and final chunk before using the length, then authenticates each chunk as it reads it. If writing or authentication fails after response headers are sent, Okuru aborts the response.

Range requests do not consume another view. Each session allows up to 32 continuation requests and limits the bytes handed to the HTTP writer across those requests to the ZIP size. The server reserves the requested bytes atomically before writing and refunds bytes it did not write, including on an interrupted connection. A process crash or Redis failure can leave a reservation charged; bytes handed to the local writer are not proof of receipt by the client. A session can therefore permit an initial copy plus up to one ZIP's worth of repeated bytes. This is not a guarantee that only one copy exists: anyone allowed to receive a file can copy it, and a session cookie can itself be shared.

By default, the resume window starts at authorization and allows five minutes plus one second per full 128 KiB of ZIP data, up to 24 hours. For example, a 1 GiB ZIP gets 2 hours, 21 minutes and 32 seconds if the share has at least that much time left. A share with only 30 minutes left limits the session to that remaining time. Pausing or resuming does not reset the clock. To use a fixed window, set `OKURU_DOWNLOAD_SESSION_TIMEOUT` to a Go duration such as `30m` or `2h`. The minimum is one second, and durations over 24 hours are capped. An invalid setting fails the POST before it reserves a view. An open transfer can continue past its deadline. Each new request requires the parent share, a valid link key and an unexpired session.

Redis stores separate `download_session_<file UUID>_<SHA-256 of cookie key>` hashes. The hash contains the archive secret encrypted with the random cookie key, never the cookie key itself. The parent file record stores only a bounded index of session-key digests. The session hashes expire independently no later than the parent TTL or configured session lifetime. An authenticated deletion removes the file record, any separately shared password and its indexed sessions using one Redis `DEL`; ACL denial for any key fails the operation before any of those records is removed. File expiration also prevents future continuation; sessions have their own expiry as a backstop. Never log or expose the share link or cookie.

The Redis account must be authorized for the session key pattern and for `EVAL`/`EVALSHA`, `HGET`, `HGETALL`, `HEXISTS`, `HKEYS`, `HSET`, `HDEL`, `HINCRBY`, `EXISTS`, `TTL`, `PTTL`, `PEXPIRE` and `DEL` on the applicable file, password and download-session keys, in addition to the existing commands. Redis is needed when creating and continuing a session. A Redis failure after a view has been reserved can prevent the redirect from being sent; this fails closed rather than exposing an unlimited download.

The server supplies a session-specific ETag for `If-Range`. It derives the archive validator from the ciphertext size, its first 4 KiB and its last 65,552 bytes, bounded by the actual file length. Okuru checks file identity, size and modification time before and after streaming and authenticates each age chunk it returns. A continuation client must preserve the scoped cookie and validator. Verify the behavior of each supported browser and proxy.
