# Download continuation

An authenticated download POST reserves one view. Once the archive has been opened and authenticated, the server creates a continuation session and sends its random key in a session-specific `Secure`, `HttpOnly`, `SameSite=Strict` cookie scoped to that file URL. A GET to the same URL with this cookie and a single `Range: bytes=…` header requests a continuation. Multiple sessions for the same link have different cookie names and validators; `If-Range` selects the right session. If multiple sessions are present and the client does not send a recognizable `If-Range`, the request is refused rather than using the wrong session. The initial POST serves the full ZIP. For both supported archive formats, Okuru authenticates the age header and final chunk before using the length, then authenticates each chunk as it reads it. If writing or authentication fails after response headers are sent, the HTTP response is aborted.

A continuation does not consume another view. It is limited to 32 requests and to a cumulative amount of data actually handed to the HTTP writer no larger than the ZIP size. The server reserves the requested bytes atomically before writing and refunds bytes it did not write, including on an interrupted connection. A process crash or Redis failure can leave a reservation charged; bytes handed to the local writer are not proof of receipt by the client. A session can therefore permit an initial copy plus up to one ZIP's worth of repeated bytes. This is not a guarantee that only one copy exists: anyone allowed to receive a file can copy it, and a session cookie can itself be shared.

Continuation sessions default to five minutes and are capped at five minutes even when `OKURU_DOWNLOAD_SESSION_TIMEOUT` specifies a longer Go duration. A shorter configured duration of at least one second is respected, and the session never intentionally outlives the remaining file TTL. An invalid setting fails a download before reserving a view. A long transfer that outlives its continuation session or the file TTL cannot be resumed through that session. Existing open transfers can continue after revocation; future requests require the parent record, its valid link key and an unexpired session.

Redis stores separate `download_session_<file UUID>_<SHA-256 of cookie key>` hashes. The hash contains the archive secret encrypted with the random cookie key, never the cookie key itself. The parent file record stores only a bounded index of session-key digests. The session hashes expire independently no later than the parent TTL or configured session lifetime. An authenticated deletion removes the file record, any separately shared password and its indexed sessions using one Redis `DEL`; ACL denial for any key fails the operation before any of those records is removed. File expiration also prevents future continuation; sessions have their own expiry as a backstop. Never log or expose the share link or cookie.

The Redis account must be authorized for the new key pattern and for `EVAL`/`EVALSHA`, `HGET`, `HGETALL`, `HKEYS`, `HSET`, `HDEL`, `HINCRBY`, `EXISTS`, `TTL`, `PTTL`, `PEXPIRE` and `DEL` on the applicable file, password and download-session keys, in addition to the existing commands. Redis is needed when creating and continuing a session. A Redis failure after a view has been reserved can prevent the initial response from being sent; this fails closed rather than exposing an unlimited download. Check deployment ACLs before enabling this version.

The server supplies a session-specific ETag for `If-Range`. It derives the archive validator from the ciphertext size, its first 4 KiB and its last 65,552 bytes, bounded by the actual file length. Okuru checks file identity, size and modification time before and after streaming and authenticates each age chunk it returns. A continuation client must preserve the scoped cookie and validator. Verify the behavior of each supported browser and proxy.
