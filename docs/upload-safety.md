# Upload validation and archive protection

Secrets are limited to 32 KiB, numeric fields to 16 bytes, and uploads to 100 files. Names must be valid and distinct after sanitization; their total size must not exceed `OKURU_MAX_FILE_SIZE`. The browser accepts up to 255 characters for a new archive password; the server applies the byte limit.

For portable extraction, new uploads reject names that have an 8.3-sized shape and contain `~` immediately followed by an ASCII digit, such as `LONGFI~1.TXT` or `FILE.D~1`. This conservative rule prevents ordinary Windows 8.3-style aliases from being submitted as distinct names, without predicting volume-specific alias generation; it also rejects some otherwise legitimate short names. Longer names such as `report~2025.txt` remain allowed. Rename rejected files before uploading. Existing archives are not changed. Windows short-name behavior depends on the volume and configuration, and this filter does not establish protection against every alias a privileged local user could assign manually. See [Microsoft's file naming guidance](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file).

## Multipart staging

Before CSRF form extraction, multipart fields are parsed in memory with explicit count and size limits. File parts are encrypted as they arrive into a private directory under `OKURU_FILE_FOLDER`, using a fresh age X25519 identity held only in process memory for that request. File contents and names are not intentionally written in plaintext into multipart temporary files. The encrypted parts are read back in a stream to create the final encrypted ZIP; this uses an extra encrypted read/write pass. CSRF fields can appear before or after the files. Request and storage limits apply before parsing.

Staging is removed before a successful upload response and on normal errors. A crash can leave encrypted staging files and their names reveal only their sequential indices; their ephemeral private key is lost when process memory disappears. Each new staging directory holds an interprocess lock. Before accepting a later upload, the application removes recognized abandoned staging directories only if it can acquire their lock without waiting; active transfers retain theirs. Legacy unmarked directories and a crash before the lock marker is published still require coordinated manual cleanup. Correct interprocess locking depends on the filesystem's locking semantics (`flock` on Unix or `LockFileEx` on Windows). The storage root and its parents must be trusted; on Unix the root must be owned by the service account or root and not writable by group or others. Windows retains verified ancestor handles during operations and opens archive/part leaves relative to anchored handles without following reparse points. Creation, publication and deletion still use paths, so pre-existing handles able to alter attributes, DACLs or reparse data remain an operational trust assumption. UNC shares, device paths and ambiguous names are refused. Windows behavior remains untested on real NTFS; see `windows-verification.md`. This protection does not exclude plaintext in application memory, swap, core dumps, the kernel page cache, clients, proxies, or snapshots of those systems; protect and configure those surfaces separately. A process or host with live access to the application can observe the password and file content.

## Final archive

The stored file is an authenticated age envelope containing an ordinary ZIP, not a natively password-encrypted ZIP. File names inside the ZIP are encrypted. The final encrypted file is closed and synchronized before metadata and its final filename are published. Publication uses a same-filesystem hard link and requires filesystem support for hard links.

For new shares with a user-provided password, the archive uses that password with age scrypt at work factor 18 (N=2^18, r=8, p=1). One derivation uses about 256 MiB of working memory, and at most one runs at a time per application process. Multiple processes, garbage collection and other services can increase peak memory. This doubles the approximate work and memory required for password guesses compared with factor 17, but also increases server cost; measure availability on the actual server before deployment. The file's Redis record contains an independent random bearer authenticator encrypted with Fernet; it does not contain the file password. The separate password-sharing link has its own Redis record containing the password encrypted with a different Fernet key present in that separate link. The server sees the password while processing an upload or a download. A strong, unique, randomly generated password remains essential: anyone who obtains the ciphertext can attempt offline guesses.

For new shares with no user-provided password, a random age X25519 identity encrypts the archive. Its private identity is encrypted with Fernet in the file's Redis record; its Fernet key is in the file link. This path does not use scrypt. Protect that link as a secret.

Existing records with an empty format continue to serve their original, unencrypted ZIP. Existing `age-v1` records retain their original password-in-metadata scheme and remain readable; existing factor-17 and factor-18 envelopes remain readable. Those archives are not migrated. Unknown or inconsistent formats are rejected. For encrypted archives the server sends a decrypted standard ZIP; bounded continuation is described in `download-resume.md`. An integrity error discovered after sending bytes aborts the response, but bytes already received cannot be recalled.

## Limits and retention

Storage reservations are shared between cooperating processes using the same trusted storage root and reliable filesystem locks. Request concurrency remains limited per process. Other roots or processes, external writes, volume changes, swap, snapshots and backups require independent controls. The reservation is a conservative estimate, not an enforced filesystem quota. Windows storage and locking support is prepared, but its tests must be executed on real Windows/NTFS before relying on it; see `windows-verification.md`.

If publication fails after creating Redis records, the application attempts to remove those records and the unpublished archive; expiry is a fallback if Redis is unavailable. Staging cleanup is separate from canonical archive reconciliation and has the limitations described above. Explicit deletion reports errors; reconciliation retries canonical archives without Redis records. No deletion guarantees physical erasure from backups, snapshots, replicas, open downloads or recipient devices.
