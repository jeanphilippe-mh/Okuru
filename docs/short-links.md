# Optional short share links

Okuru can display a short redirect for newly created browser shares without changing the existing long share URL, its Fernet key, or its Redis record. New links have the form `https://share.example.com/<alias>`, without a path prefix. The browser follows a temporary redirect to the original relative path; the original share remains authoritative for expiration, view counts, deletion, and file downloads. Existing links, API links and deletion links remain unchanged. A separately created password link for a protected file can also be shortened. If alias creation fails, the confirmation page displays the original link instead.

The root path handles both original secret tokens and short aliases. Exactly 22 or 43 Base64URL characters at the root are reserved as alias candidates; avoid introducing root routes or static files with either form, because routing may otherwise conflict. Current original share tokens have a distinct format. Previously issued 43-character aliases continue to resolve until they expire.

## Configuration

Creation of short links is disabled unless both `OKURU_SHORTLINK_REDIS_DB` and `OKURU_SHORTLINK_PUBLIC_ORIGIN` are set. Resolution of previously issued aliases depends on the configured database, not on the origin setting. The origin must be a canonical HTTPS origin with no credentials, path, query or fragment, for example `https://share.example.com`. It must be the origin that actually serves Okuru; the application does not infer it from request headers. The short-link database must be a different logical Redis database on the same server as `REDIS_DB`. Use a database reserved for this feature and never clear other applications' data.

`OKURU_SHORTLINK_BITS` controls the randomness of newly created aliases. Set it to `128` for 22 characters or `256` for 43 characters; the default is `128`. Any other value prevents alias creation and the application falls back to the original long URL. Previously created aliases of either size continue to resolve regardless of this setting. Restart the service after changing its environment file so the running process receives the new value.

The Redis server must support `PEXPIRETIME` (Redis 7 or later) and `PXAT`; its account needs SELECT for both databases and permission for PEXPIRETIME in the primary database and EVAL/EVALSHA, TIME, DBSIZE, SET, STRLEN and GET in the short-link database. Lua commands are subject to Redis ACL checks. Verify actual Redis version, logical databases and ACLs before enabling. If configuration, access, capacity, cryptography or storage fails, share creation returns the original long URL instead of failing a share that has already been created.

The short-link database has a fixed admission limit of 4096 keys; the check and conditional insertion are atomic. That limit counts all keys in the chosen database. Aliases for shares deleted or consumed early remain until their original expiry and can exhaust this limit; at capacity, new shares use their long URLs. Monitor the database key count, Redis memory, rejected writes and evictions; provision persistence and backups to match required link availability. The limit is separate from the main database's secret limit, but separate logical databases on the same Redis instance share memory, eviction policy, CPU and availability. If an alias is lost or Redis is unavailable later, an already shared short link will not work, and its original link is not displayed as a separate backup on the confirmation page. Recovery requires restoring the corresponding unexpired alias record. A backup containing only Redis records does not reveal the destination without the alias, but possession of the alias permits its decryption.

## Security and lifecycle

New bearer aliases contain either 16 random bytes (128 bits), encoded as 22 unpadded Base64URL characters, or 32 random bytes (256 bits), encoded as 43 characters, according to the configured setting. HKDF-SHA-256 with independent fixed domain labels derives a Redis lookup key and a per-alias AES-256-GCM key; Redis stores an authenticated encrypted record containing the share type and existing token, not the alias or the destination in clear. Deriving a 256-bit encryption key does not increase a 128-bit alias's entropy, and AES-GCM uses a 128-bit authentication tag. The server receives the alias and reconstructs the long path: this is not end-to-end encryption.

Resolution accepts only canonical aliases and reconstructs one of two local paths from a validated existing token. It never accepts an arbitrary destination or fetches the target. GET and HEAD return a temporary redirect with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. The browser then sees the original link. The alias itself is a bearer credential; anyone with it can resolve the original link. Do not disclose it in logs, analytics, issue reports or screenshots.

Each application process permits at most eight concurrent alias resolutions; excess requests receive HTTP 503 with `Retry-After: 1`. This limits contention for the short-link Redis pool but is not a per-client rate limit or protection against distributed denial of service.

The alias expiry is set to the original record's absolute Redis expiry, using the same server clock; records expiring within one second are not shortened. A share deleted or exhausted early may leave a redirect until that expiry, but the destination remains responsible for refusing access. The shortener does not consume views itself. Clients or link-preview bots can follow a redirect; validate their behavior using disposable test shares. HTTP API URLs and deletion URLs are not shortened.

The application logger records route patterns rather than concrete URLs, but this does not configure or prove the behavior of the actual reverse proxy, WAF, observability stack, clients or browser history. Check that those systems do not record alias paths, destination URLs, Location headers, Referer headers or request bodies. Do not weaken a WAF to achieve this.
