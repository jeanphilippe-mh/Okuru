# Content Security Policy and Apache

Okuru generates a new cryptographically random nonce for each rendered HTML
response and includes it in the response's Content Security Policy (CSP) and
its authorised script elements. HTML responses are marked `private, no-store`.
Do not cache these responses or combine an old HTML body with a new CSP. The
service worker does not cache navigations.

The application owns the full CSP for its rendered HTML. A second enforced CSP
is cumulative and may block the scripts even when the application nonce is
correct. Keep the deployed Apache configuration and `router/csp.go` coordinated.

Each local JavaScript file loaded by a `<script src>` element also has a
SHA-512 Subresource Integrity (SRI) value in its template. The browser refuses
the file if its bytes do not match. These hashes are HTML attributes, not CSP
hash sources; the per-response nonce remains responsible for script
authorization. The SRI check does not cover inline scripts, or the worker
script loaded separately by `navigator.serviceWorker.register()`. It does not
protect against an attacker who can also change the document and its hashes.

When updating a local script, update every associated `integrity` attribute and
run `node --test tests/sri.test.cjs`. Deploy the executable, `views/` and
`public/` from the same revision. A stale or modified asset, including one
returned by a cache, fails integrity and will not execute. Normal HTTP content
compression is supported; intermediaries must not rewrite JavaScript bytes.

## Apache configuration without a fallback policy

For the deployment that delegates CSP to Okuru, remove the old unconditional
`Header ... Content-Security-Policy` line from the virtual host without adding a
second CSP. Keep the other security headers. Pages rendered by Okuru receive its
nonce-based policy; responses generated by Apache or ModSecurity, and any other
response without an application CSP, do not acquire a fallback policy. In
particular, the separately served service-worker script has no worker-specific
CSP unless one is configured elsewhere. Check the actual response headers and
review whether these consequences are acceptable for the installation.

The former style hash was not found in the versioned Okuru templates; verify
independently managed error pages for visual regressions. The local Apache
contract test exercises a fallback option with `mod_proxy_http`; it does not
establish the behavior of the no-fallback production configuration. Test the
actual `mod_proxy_http2` and ModSecurity stack in staging. Verify exactly one
CSP on Okuru-rendered pages, the nonce and `no-store`; also test forms, sharing,
downloads and the service worker. Never trust a nonce supplied by a client.

First rehearse the following sequence in a staging environment using the actual
Apache HTTP/2 proxy and ModSecurity configuration. Expect a maintenance window:

1. Save the currently deployed executable, `views/`, `public/` and Apache
   configuration. Prepare the new binary, views, public assets and Apache
   configuration in a separate directory without activating them, then check
   the Apache syntax and effective virtual host. Do not run `git pull` in the
   live directory: the running application loads views from disk.
2. Stop or drain the old application before switching the Apache header. During
   this interval Apache may return an error page; the response has no fallback
   CSP when Apache itself generates it.
3. Replace the executable, `views/` and `public/` together while the application
   is stopped, preserving `.env`, `data/` and all other installation state.
   Activate the new Apache configuration and restart Apache in a planned window
   before starting the new application. A graceful reload can leave old workers
   or connections serving the old policy. A restart interrupts connections; do
   not claim a zero-downtime transition. Verify the single CSP, nonce rotation,
   SRI and browser flows above, plus the service-worker fetch and cache behaviour.
4. If configuration validation, startup or verification fails, stop the new
   application, restore and validate the saved Apache configuration, reload it,
   then restore the saved executable, views and public assets together and start
   the old application. Confirm recovery in a browser.

Removing the old Apache policy while an old application without an application
CSP is serving requests leaves those pages without CSP. Keeping the old enforced
Apache policy alongside the new nonce policy can block scripts. Perform the
production switch only after staging checks and an explicit deployment decision.

For example commands and rollback steps on Debian, see
[Debian CSP deployment](csp-deployment-debian.md). For the integrity update
procedure and its limits, see [Subresource Integrity](subresource-integrity.md).
