# Content Security Policy and Apache

Okuru generates a new cryptographically random nonce for each rendered HTML
response and includes it in the response's Content Security Policy (CSP) and
its authorised script elements. HTML responses are marked `private, no-store`.
Do not cache these responses or combine an old HTML body with a new CSP. The
service worker does not cache navigations.

The application owns the full CSP for its rendered HTML. Keep its policy in
`router/csp.go` aligned with the Apache fallback below when changing other CSP
directives. A second enforced CSP is cumulative and may block the scripts even
when the application nonce is correct.

## Apache fallback for the share.jeanphilippe.io virtual host

Replace the existing unconditional `Header always set Content-Security-Policy`
line with the following single line. Keep the other virtual-host headers as
they are. It sends a policy only when the backend did not supply one, including
for errors generated by Apache. It blocks scripts on fallback pages, while
retaining `connect-src` for the service worker and the other existing controls.

```apache
Header always set Content-Security-Policy "default-src 'none'; script-src 'none'; worker-src 'self'; require-trusted-types-for 'script'; form-action 'self'; connect-src 'self'; style-src 'self'; img-src 'self' data:; manifest-src 'self'; font-src 'self'; base-uri 'none'; child-src 'none'; frame-src 'none'; frame-ancestors 'none'; object-src 'none'; upgrade-insecure-requests" "expr=-z %{resp:Content-Security-Policy}"
```

Do not use `Header always setifempty` as a substitute: the Apache response-header
tables can cause it to add a second CSP even when the backend already sent one.
The fallback intentionally has no script hashes or nonce, so scripts embedded
in Apache-generated error pages cannot run. If those pages require JavaScript,
review and test them before enabling this configuration. The former style hash
was not found in the versioned Okuru templates; check any independently managed
Apache and ModSecurity error pages for visual regressions.

The Apache contract test covers a local Apache with `mod_proxy_http`. The
production deployment uses `mod_proxy_http2` and ModSecurity and must be tested
in that actual configuration before release. In particular, verify exactly one
enforced CSP for successful pages, application errors, static assets and
Apache-generated errors. Test the service worker, forms, upload sliders, sharing,
and download flows in a browser, and confirm the console has no unexpected CSP
violations. A nonce must change on reload and match the authorised script tags;
never trust a nonce supplied in a request header.

First rehearse the following sequence in a staging environment using the actual
Apache HTTP/2 proxy and ModSecurity configuration. Expect a maintenance window:

1. Save the currently deployed application and Apache configuration. Prepare
   the new binary and Apache configuration without activating either, then check
   the Apache syntax and effective virtual host.
2. Stop or drain the old application before switching the Apache header. During
   this interval Apache may return an error page; this avoids serving old HTML
   under the fallback policy, which blocks its scripts.
3. Activate the new Apache configuration, reload Apache, and start the new
   application. Verify the single CSP, nonce rotation and browser flows described
   above, as well as the service-worker fetch and cache behaviour.
4. If configuration validation, startup or verification fails, stop the new
   application, restore and validate the saved Apache configuration, reload it,
   then restore and start the old application. Confirm recovery in a browser.

Removing the old hashes from Apache while the old application is serving
requests blocks its inline scripts. Keeping the old enforced policy alongside
the new application policy blocks those scripts as well. Perform the production
switch only after the staging checks and an explicit deployment decision.
